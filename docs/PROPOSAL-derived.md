# 제안 — 가려서 만든 파생 자료를 Claude 로 보내는 길

> **상태: 제안 · 구현 없음 · 결정 1·2 승인 (PLAN 06 문구 수정 · L1 설계를 제안으로 올림) · 결정 3 (L2) 확인 중.** 이 문서는 PLAN · SPEC 을 바꾸지 않는다. 결정이 나면 그때 PLAN 06 · SPEC 에 옮기고 이 문서는 지운다.
> 보안 부서 질문 9 ([kit/security-brief.md](../kit/security-brief.md)) 와 이어진다 — 이 도구는 거기서 허락한 등급까지만 만든다.

## 1. 요청과 부딪히는 조항

요청: "사내 데이터를 분리하되, 필요하면 마스킹이나 정규화를 해서 Claude 에 보내는 과정을 아주 정교하게."

| 조항 | 내용 | 부딪히는 정도 |
|---|---|---|
| PLAN 06 (D1–D8 머리말) | "자동으로 가려서 보내지 않는다 — 가린 결과를 사람이 보지 않으면 확정이 아니다" | 뒷절 (사람이 가린 결과를 본다) 은 그대로 지킨다. 앞절의 "자동으로 가려서" 만 손본다 |
| PLAN 01 비목표 | "원자료를 '안전하게 만들어' 보내는 도구가 아니다. 그런 변환은 없다고 보고 설계한다" | **정면.** 이 요청은 그 변환이 있다는 쪽이다 |
| AL-04 · D4 | 바깥으로는 일의 모양만 — 숫자 · 파일 · 코드 원문이 없다 | 표본 값 (숫자) 이 나가려면 D4 의 예외가 필요하다 |
| L-05 | 가려도 구조 · 수치 관계로 재식별된다 · 여러 번 모으면 그림이 된다 (모자이크) | 이 요청이 만드는 새 위험의 이름이다 |
| AL-10 | 실데이터는 보안 부서 승인 뒤 | 파생 자료도 실값에서 나오면 실데이터로 센다 |

## 2. 결론부터

- **가림은 "제안" 이지 "안전" 이 아니다.** 안전은 (가) 결정적 검사 D1–D7 을 *가린 결과* 에 다시 돌리고 (나) 사람이 *가린 결과* 를 보는 것에서 나온다. 이 구조는 W-07 (제안 → 확정) 과 같아서 PLAN 06 의 정신과 맞는다. 고칠 문구는 "자동으로 가려서 **보내지** 않는다" → "가려서 **제안** 하되, 보내는 것은 D1–D8 을 통과하고 사람이 본 바이트뿐이다" 하나다.
- **비목표는 그대로 둔다.** 가림이 안전하다고 주장하지 않는다. 가림이 새지 않았다는 것은 증명할 수 없는 경우가 있고, 그때는 보내지 않는다.
- **단계로 나눈다.** 값이 하나도 파생되지 않는 단계 (L0 · L1) 와 실값에서 파생되는 단계 (L2 · L3) 는 위험의 종류가 다르다. 앞쪽은 구조상 새지 않게 만들 수 있고, 뒤쪽은 막을 수는 있어도 "새지 않는다" 를 보일 수 없다.

## 3. 단계

| 단계 | 나가는 것 | 정보가 어디서 오나 | 안전의 근거 | 권고 |
|---|---|---|---|---|
| **L0 모양** (지금) | 닫힌 서술자 — 화면 · 항목 · 단계 · 꼴 (`숫자 · 단위 있음`) | 사내 LLM 이 쓴 모양 | D1–D8 | 있다 |
| **L1 합성 표본** | 서술자로 *Diode 가 새로 지어낸* 표본 (열 종류 · 행 수 구간 · 결측 비율 구간 → 지어낸 값) | 서술자뿐 (정보량이 L0 와 같다) | 아래 3.1 — 구조상 실값이 못 낀다 | **보안 부서 9-(나) 답 뒤에 만든다.** 설계는 지금 |
| **L2 파생 표본** | 실값에서 파생한 것 — 토큰화 · 정규화 · 순위 · 범주 묶음 · 노이즈 | 실값 | 증명 불가 (3.2) | **기본으로 만들지 않는다.** 9-(다) 가 명시적으로 허락할 때만 |
| **L3 정규화한 글 · 코드** | 식별자 · 문자열 · 주석을 지운 코드, 사전 단어를 토큰으로 바꾼 글 | 실제 글 · 코드의 *구조* | 글은 말 봉인 (이미 있음). 코드는 구조 자체가 비밀일 수 있다 | 글: 있다. 코드: 합성 재현 (`lib`, D5a) 으로 한정 — 지금 그대로 |

### 3.1 L1 이 구조상 새지 않는 까닭 — "다시 만들어 대조한다"

- 표본 값은 사내 LLM 이 쓰지 않는다. brief 에는 서술자와 *시드의 해시* 만 있고, 값은 Diode 의 생성 함수 `f(서술자, 시드)` 가 만든다. 시드는 자문마다 `secrets` 로 뽑는다 (AL-05 와 같은 모양).
- 검사기 (seal) 는 바깥으로 나갈 표본을 서술자 · 시드로 **다시 만들어 한 글자도 다르지 않은지** 대조한다. 다르면 막는다. 그래서 사내 LLM 이 표본 칸에 실값을 끼워 넣을 길이 없다 — D4 의 숫자 금지는 *자유 글* 에만 걸려 있고, 이 표본은 자유 글이 아니라 "재생성으로 증명되는 칸" 이다.
- 생성 함수는 공개 이름 · 자리 글만 쓴다 (`item_1`, `col_3`, 균등 난수). 서술자가 실값에서 새는지 (예: `범주 · 값 7개 안팎` 의 7 이 실제 개수인가) 는 L0 가 이미 안고 있는 위험이고, L1 은 그것을 키우지 않는다.
- 시험: 카나리아 변형 코퍼스 (T3) 를 그대로 쓴다. L1 은 실값이 입력에 없으므로 "새는 비율 0" 이 **구조로 증명** 된다 (시험은 확인일 뿐).

### 3.2 L2 가 증명되지 않는 까닭

| 방식 | 하는 일 | 남는 위험 |
|---|---|---|
| 토큰화 · 마스킹 | 값을 `PH_` 같은 토큰으로 | 길이 · 형식 · 빈도가 그대로 남는다. 사번 꼴 · 로트 번호 꼴이면 형식이 곧 식별이다. 같은 값이 같은 토큰이면 빈도 분포가 나간다 |
| 정규화 (z-점수 · min-max) | 크기를 지우고 비율만 | 순서와 상대 간격이 보존된다. 이상치가 한 건이면 그 한 건이 식별되고, 공개 통계와 대조하면 풀린다 |
| 범주 일반화 (k-익명) | 희귀한 값을 뭉친다 | k 보다 작은 칸을 억제해야 하고, 준식별자 조합마다 따로 봐야 한다 |
| 노이즈 (차등 프라이버시) | 값에 잡음을 더한다 | 잡음 예산 (ε) 을 자문 *사이에도* 합쳐 관리해야 한다. 자문마다 토큰은 새로 뽑아도 **통계는 누적** 된다 (L-05) |
| 합성 데이터 생성 | 모델이 비슷한 표를 만든다 | 학습 자료를 기억해 되뱉는다. 어떤 값이 기억된 것인지 알 수 없다 |

- 위 어느 것도 "실값에서 바깥으로 가는 정보가 0" 이 아니다. 목표 G1 (카나리아 0) 은 **문자열이 새는지** 만 잡는다 — 통계적 재식별은 못 잡는다. 시험을 하려면 새 공격 시뮬레이션 (공개 보조 자료와 합쳐 재식별해 보는 것) 이 따로 필요하고, 합격선은 보안 부서가 정한다.
- 가린 결과를 사람이 눈으로 보는 것 (D8) 도 이 위험은 못 거른다. 사람은 문자열이 새는지는 알아보지만 통계가 새는지는 알아볼 수 없다.

## 4. L2 를 허락받았을 때 지킬 장치 (요구사항 — 구현 아님)

1. **기본 꺼짐.** `policy.derived_level` 은 `0` 이고 창에서 사람만 바꾼다 (AL-10 처럼 확인 글을 쳐야 켜진다). 환경 변수 · 명령줄 · 시험용 우회 없음.
2. **열 단위 허락.** 열마다 사람이 허락해야 한다. 기본은 전부 거부. 허락한 열에 어떤 변환을 쓰는지도 같이 적는다.
3. **변환은 결정적 코드가 한다.** 사내 LLM 이 값을 보고 "가려서 써 주는" 방식은 쓰지 않는다 (그 글이 곧 새는 길이다).
4. **가린 결과를 다시 검사한다.** D1–D7 을 변환 *뒤* 의 바이트에 돌리고, 확정 창은 *가린 결과* 를 그대로 보인다. 원본과 대조하는 화면은 안쪽에만 있고 바깥으로 나가지 않는다.
5. **재식별 방어.** 최소 셀 크기 (k) 미만 억제 · 이상치 자르기 · 정밀도 제한 · 행 수 상한. 수치는 보안 부서가 정한다.
6. **누적 상한.** 주제별로 보낸 파생 자료의 총량 상한 (모자이크, L-05). 감사 기록에는 변환 종류 · 열 수 · 행 수만 남기고 값은 남기지 않는다.
7. **시험.** 문자열 카나리아 (T3) + 재식별 공격 시뮬레이션 (새로 만든다, T3b). 합격선 없이 켜지 않는다.

## 5. 권고 — 순서

1. **지금 한다 (결정이 나면):** PLAN 06 문구를 "제안 → 확정" 으로 고치고, 비목표에 "가림이 새지 않았다는 것을 증명할 수 없으면 보내지 않는다" 를 더한다. 문서만 바뀐다.
2. **필요한 사례부터 모은다.** "값이 있어야 Claude 가 일할 수 있었다" 는 사례를 지어낸 것 (합성) 으로 셋만 적어 본다. 화면 설계 · 기획의 대부분은 *열의 종류 · 개수 · 관계 · 흐름* 이면 충분하고, 그건 L0 · L1 로 된다. 사례가 L1 로 모자라면 그때 L2 를 논한다.
3. **L1 은 보안 부서 9-(나) 답 뒤에 만든다.** 그 사이에 설계 (서술자 닫힌 목록 · 생성 함수 · 재생성 대조) 는 이 문서대로 둔다.
4. **L2 는 9-(다) 의 명시적 허락 + 4 의 장치 + 합격선이 *모두* 있을 때만.** 하나라도 없으면 만들지 않는다. 사람이 "급하니 일단" 하고 켜는 길을 코드에 만들지 않는다.

## 6. 결정 요청

1. PLAN 06 의 "자동으로 가려서 보내지 않는다" 를 "가려서 **제안** 하되 보내는 것은 검사와 사람 확정을 통과한 바이트뿐" 으로 고쳐도 되는가?
2. L1 (합성 표본) 의 설계를 SPEC 에 *제안* 으로 올려도 되는가? (구현은 보안 부서 답 뒤)
3. L2 는 (가) 보류 — 권고 / (나) 설계만 / (다) 구현 중 어느 쪽인가?
4. "값이 있어야 했던" 실제 사례가 있는가? 있다면 합성으로 바꿔 두세 개만 (이름 · 수치 없이 모양만) 알려 달라.
